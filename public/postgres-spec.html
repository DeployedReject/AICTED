PostgreSQL

Preparation

D1 remains the active database. The migration form stores a destination profile; it does not connect to PostgreSQL, copy data, or switch traffic.

Connection

Property Requirement
Version PostgreSQL 16 or later, UTF-8 encoding. A dedicated application database, separate from unrelated services.
Network A hostname and port reachable by Cloudflare Hyperdrive. Use connection pooling; do not open an unbounded connection per request.
TLS Encrypted transport required. Prefer full certificate and hostname verification. Use the verification options supported by the selected Hyperdrive origin configuration.
Credentials A dedicated application role. Store the connection password in Hyperdrive/Cloudflare secrets during provisioning, never in the browser, migration profile or Git.
Roles A separate migration owner applies schema changes. The application role must not be a superuser or schema owner, and must not have CREATE, ALTER, DROP, TRUNCATE or replication privileges.

Schema

Download target SQL. This is the target database schema, not an executable D1 migration. Review it in a disposable PostgreSQL database first.

Table Purpose
officials Verified IDs, designation, Bureau, explicit authority, reporting lines, PBKDF2 password hash and salt. Self-references must not form cycles.
sessions SHA-256 hashes of opaque session tokens, expiry as epoch seconds, and separate official/IT portal scope. Expired sessions must not authenticate.
institutions, tags Unique Permanent IDs and the controlled tag catalogue.
cases Ownership, intake decision, lifecycle, escalation, JSONB tag arrays, original description, receipt/due/update timestamps and dataset boundary.
case_events Append-only chronological history. Deny UPDATE, DELETE and TRUNCATE to the application role; preserve the immutable-history trigger.
case_grants, coordination_requests Selected-official grants, two approval stages, rejection/revocation and timestamps. A partial unique index permits only one open request per case and selected official.
messages Sender/recipient IDs and optional case references, with access checked on both send and read.
workspace_settings, migration_settings Non-secret IT settings, isolated between production and demo.
tag_cache, inference_usage Expiring cached model results and atomic daily quotas.

Data contract

  • Preserve every ID exactly, including leading zeroes. IDs remain text; do not replace them with integer sequences.
  • Return timestamps to the API as UTC ISO 8601 strings. Keep session/cache expiry as integer epoch seconds. Do not reset receipt dates during migration.
  • Keep JSONB tags as arrays of catalogue codes. Preserve is_demo, active and escalated as numeric 0/1 values in API responses.
  • Keep the existing lifecycle and intake values unchanged. Intake approval and case disposal remain separate.
  • Manager scope follows explicitly configured reporting lines. Coordination grants apply to selected IDs and never spread to a whole Bureau or to the recipient's manager.

Adapter

The current Workers use D1's SQLite API. Before switching, implement a PostgreSQL adapter with parameterised queries, transactions and pooling. A saved hostname alone cannot activate PostgreSQL.

  • Convert ? placeholders to PostgreSQL parameters; replace SQLite full-text MATCH with PostgreSQL indexed text search, and json_each with JSONB operations and boolean sums with filtered aggregates.
  • Replace D1 batch calls with transactions. Use conditional updates/row locks and affected-row checks so competing approvals cannot create duplicate events or grants.
  • Preserve recursive reporting scope, demo separation, revoked-grant filtering, all current pagination bounds and server-side access checks.
  • Do not expose a database connection or secret to React. Only the authenticated web entry may call the private casework service.

Cutover

  1. Back up D1 and retain a tested rollback plan. Prepare the schema, restricted runtime role, indexes, TLS and Hyperdrive binding.
  2. Pause writes for the export/import window, or implement and verify a change-capture process before using one. Import officials in reporting order, then institutions, tags, cases, events, grants, coordination, messages and settings.
  3. Compare row counts, IDs, timestamps, foreign keys and hashes. Keep demo records isolated. Invalidate existing sessions at cutover; do not expose session tokens in exports.
  4. Run access-denial tests, no-self-approval checks, both coordination stages, selected-user sharing, revocation, append-only history, messaging, quotas, pagination and concurrent approval tests.
  5. Check query plans and latency against assignment, institution, event and grant indexes. Enable traffic only after the adapter and migration checks pass.
  6. Verify the new backend, then resume writes. After new writes reach PostgreSQL, rollback requires reconciling those writes; do not simply point traffic back at an old D1 snapshot.
