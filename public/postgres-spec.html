Database setup

The Database settings page controls the application’s live connection. Supported targets are Cloudflare D1 and PostgreSQL 16+. The original D1 retains the encrypted connection registry, IT recovery accounts and delivery settings.

Before connecting

Cloudflare D1 PostgreSQL
Create a dedicated database. Provide its account ID, database ID, display name and an API token with D1 Read and Write permissions for that account. Create a dedicated UTF-8 database on PostgreSQL 16 or later. Provide a public host or pooler endpoint, port, database name, user and password. TLS is required.
Initialization needs write access, including table and trigger creation. Cloudflare API requests carry the saved, encrypted token. Initialization needs CREATE privileges for tables, indexes, functions and triggers in the public schema. Normal use needs SELECT, INSERT, UPDATE and DELETE on application tables. Connections use at most one client per database request, with prepared statements disabled for pooler compatibility.

Schema contract

Download the complete PostgreSQL schema. You can also initialize a completely empty destination directly from Database settings. Case document metadata is stored in case_documents; document contents remain in private R2 storage and must be backed up separately. The application requires schema version 10 in app_schema, all supplied columns, history and email triggers, and an indexed official directory. Do not adapt arbitrary tables by changing only the version marker.

The maintained schema uses integer flags, UTF-8 text identifiers, UTC ISO-8601 timestamp strings and JSON-array text for case tags. Preserve those boundary formats. Text columns use C collation so transfer ordering agrees with SQLite. Do not convert timestamp text to locale-specific dates or rename columns. Required PostgreSQL helpers include json_each(text), scalar min(text,text) and max(text,text). The server adapter binds parameters and maps the directory search to PostgreSQL full-text search.

Case events and administrator audit entries are append-only. Officials have a job designation, a reporting manager and a separate report scope. Bureau-wide reports require an explicitly configured manager with bureau scope. The supplied triggers enqueue production formal updates; comments and demo records do not trigger outgoing mail.

Activate a destination

  1. Save the connection. Credentials are encrypted with AES-GCM; saving does not switch traffic.
  2. If the destination has no tables, select Initialize empty database. Initialization never overwrites an existing schema.
  3. Test connection. The check validates the schema, required triggers and read/write permissions.
  4. Choose Copy current data or Use prepared database. Copy requires empty application tables, apart from reference categories and bureaus. Prepared mode requires your production IT account ID in the destination.
  5. Type the connection name and activate. The server pauses application database access, copies indexed chunks and verifies record hashes. Do not write to either database from an external client while this runs.
  6. Refresh status, or leave this page open for temporary progress updates. Server alarms continue the transfer after the page closes.

Failure and rollback

Failures before activation leave the source active. Partial destination records are retained. The failed-copy panel can discard that incomplete destination schema, after you confirm its name, so you can initialize and retry. It cannot reset the active, original or previous database.

For a later rollback, select the previous connection and activate it in prepared mode. This uses that database’s earlier records. It does not merge or recover changes made after switching away. Export or reconcile those changes before reverting if they must be retained.

Recovery and secrets

IT sign-in and database management remain attached to the original D1 control store, even when the chosen application connection fails. Retain the original D1 binding and the same CONFIG_KEY when redeploying. Losing that key makes saved credentials unreadable. Normal settings responses never return plaintext credentials; revealing one is an explicit, audited action.

Application sessions and account permissions are read from the active dataset. An in-flight request cannot write using a different connection generation from the one it read. A database switch may therefore ask users to reload or sign in again.

Database profiles, routing state and control audit history are kept outside application transfers. Keep a separate backup of the original D1 and its encryption secret. Do not publish API tokens, passwords or database exports.
